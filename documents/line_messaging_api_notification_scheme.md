# 監視系タスクの検知結果をLINEに通知するには、LINE Messaging APIのpushを使う

## 結論

Web監視・スクレイピング系タスク（空き枠検知、新着物件検知等）で「検知結果を人間のスマホにプッシュ通知したい」場合、**LINE Messaging APIのpushメッセージ**（`https://api.line.me/v2/bot/message/push`）をcurlから直接叩く方式が、追加インフラ不要かつ確実に動く。LINE Notifyは既にサービス終了しているため選択肢にならない。この方式はサグラダ・ファミリアのチケット監視タスク（`tasks/done/20260902-local-headless-browser-schedule/`）で実証済みで、SUUMO新着物件監視タスク（`tasks/doing/20260917-suumo-new-listing-watcher/`）でも同じ認証情報・実装パターンをそのまま再利用している。

## 前提構成

- LINE公式アカウント（Messaging API有効化済み）のチャネルアクセストークンと、通知先ユーザーのuserIdが必要
- 認証情報はコード直書きせず、ローカルの設定ファイルに分離して置く（実例: `~/.config/claude-headless/line_channel_access_token`、`~/.config/claude-headless/line_user_id`）。新規タスクで再利用する場合はこのパスをそのまま参照できる
- 個人（1対1）宛て送信は`to`にuserIdを指定するだけで完結する

## ハマりポイント

### グループ宛て送信は技術的に可能だが実用上は割に合わない

`push`の`to`にgroupIdを指定すればグループ送信自体は可能。しかしgroupIdの取得には「ボットをグループに招待した状態でグループ内発言を受信するWebhookサーバー」が必須で、事前取得の手段がない。cron定期実行のみのシンプルな構成（常時稼働サーバーなし）から一気にWebhook受信基盤の構築が必要になりスコープが跳ねるため、個人宛て送信で妥協するのが現実的な落とし所。

### 画像添付には公開HTTPS URLが必要、画像ホスティング先の選定に注意

Messaging APIのimageメッセージは画像バイナリを直接送れず、公開アクセス可能なHTTPS URLを渡す必要がある。当初試した`0x0.st`は「AI botnetによるスパムが酷いためアップロード機能停止中（再開時期未定）」という状態だった。代替として**ImgBB API**（`curl -X POST https://api.imgbb.com/1/upload -F key=<APIキー> -F image=@<ファイル>`）が無料・無期限（`expiration: 0`指定時）で安定して使え、レスポンスの直リンクをそのままimageメッセージのURLに使える。ただし無料枠にはレート制限があり、短時間に連続アップロードすると失敗することがある（その場合はテキストのみ送信にフォールバックする設計にしておくと安全）。

### 無料プランの月200通枠を考慮した通知頻度設計が必須

Messaging API無料プランは月200通まで。「監視のたびに毎回（空き有無に関わらず）テキスト＋画像2メッセージを送る」設計にすると、1日9回実行しただけで月間約540通に達し即座に枠超過する。**「状態に変化があった／注目すべき事象を検知したときだけ通知する」**設計にしないと簡単に破綻する。実際にサグラダ監視タスクでは「毎回通知」を一度試して枠超過が判明し、「検知時のみ通知」の当初設計に差し戻した経緯がある。

### メッセージの文字数上限

1メッセージ5000文字が上限。安全マージンを見て4500文字程度で分割するとよい（SUUMOタスクでの実装例）。

## 推奨アーキテクチャパターン

1. **決定論的スクリプト**（Playwright等、LLM不使用）が毎回の監視実行を担当し、判定結果をログファイルに1行追記する。ここはLLMを介さず高速・低コストに回す
2. 監視結果に「通知すべき変化」があった場合**のみ**、Step2としてLLM（`claude -p`＋専用promptファイル）を呼び出し、人間可読な通知文面を生成させてLINE pushで送信する

このように「安価な定期チェック（決定論的）」と「たまにしか起きないLLM生成の通知」を分離することで、月間メッセージ数と実行コストの両方を抑えられる。
