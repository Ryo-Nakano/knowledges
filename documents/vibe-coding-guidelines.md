# バイブコーディング実践ガイドライン

> 出典: Qiita記事「エンジニア歴20年の私が、素人バイブコーディング勢に物申す」(by Akira-Isegawa)

AI(バイブコーディング)で作ったプロダクトを**本番リリースする前に守るべき最低限の作法**をまとめたガイドライン。

---

## 第一条：セキュリティだけは絶対に守れ

### インフラ選択の原則

| レイヤー | ツール例 | バイブコーダーの推奨度 |
|---|---|---|
| IaaS | AWS / GCP / Azure | ❌ まだ手を出すな |
| PaaS | Vercel / Firebase / Supabase | ⚠️ まだ早い（罠を理解してから） |
| SaaS型ビルダー | Lovable / Bolt.new | ✅ まずここを使え |

- PaaSのセキュリティルールはデフォルトが「全許可」に近い場合がある（FirestoreのテストモードなどFirestore RLS等）
- SaaS型が「安全側の既定値」を提供してくれる

### シークレット管理の鉄則

- APIキー・秘密鍵・トークンは**コードに直書き禁止**（Secrets/環境変数に入れる）
- 公開鍵と秘密鍵を混同しない（ブラウザOK vs 漏れたら終わり）
- **権限は最小化**、テスト用と本番用で鍵を分ける
- エラーログ・画面キャプチャ・AIへの質問文に鍵を貼らない（漏えいはだいたいそこから）
- 漏えいを前提に再発行・無効化手順を先に確認しておく

### 認可の落とし穴：IDORに注意

「ログインできる」と「他人のデータが見えない」は**まったく別の問題**。

```
https://myapp.com/orders/12345 → 12345 を 12346 に変えたら他人の注文が見えないか？
```

→ **データを取得するたびに「これは今ログインしているユーザーのものか？」をサーバー側でチェックせよ。**  
（AIに「注文を取得するAPIを書いて」と頼むと、このチェックを忘れたコードを返すことが多い）

### 入力バリデーション

- クライアントサイドのバリデーションはUX補助にすぎない → **必ずサーバー側でも検証せよ**
- ファイルアップロードは特に危険：拡張子・MIME・マジックナンバーの**三点確認**が必要
  - 拡張子だけで「画像だ」と判断 → 実行ファイルが混入
  - ファイル名をそのまパスに使用 → パストラバーサル（`../../etc/passwd`）
  - サイズ上限なし → ディスク枯渇
  - SVGをそのまま表示 → XSS
- 自前実装をせず、SaaSの既定の仕組みに乗るのが最も安全

### ライブラリの確認

AIが提案するライブラリを鵜呑みにしない。入れる前に確認すること：

- 公式リポジトリ（npm、PyPI）で実在を確認
- 最終更新が直近1年以内か
- GitHubスター数・Issue数・メンテナ活動
- ライセンス（GPL系を商用で使うと問題になる）
- `package-lock.json` や `requirements.txt` でバージョン固定

> AIはハルシネーション（存在しないライブラリ名の提案）や、タイポスクワッティングの罠になっているパッケージを推すことがある。

### エラーメッセージ

- 本番環境でスタックトレースをそのままユーザーに返さない
- ユーザーへは抽象的なメッセージ（「処理に失敗しました」）のみ返す
- 詳細はサーバー側ログにだけ残す

### 社内システムも油断しない

「外部公開していないから安全」は誤り。社内が最も危ない：

- 漏洩の主因は外部攻撃より**内部持ち出し・マルウェア感染**
- テレワーク・BYOD・クラウド普及で「内側＝安全」は崩壊（→ **ゼロトラスト**の考え方）
- 漏えいしていても検知が遅れやすい（数ヶ月気づかない事例も実在）
- セキュリティの甘い社内システムが**踏み台（ラテラルムーブメント）**に使われる

#### 社内AIツールの利用ルール

- 会社が承認していないAIツール・MCPを**勝手に使うな**（シャドーITはAIだと特に厳しく扱われる）
- 私用アカウントで社内業務をするな
- 機密コード・顧客データ・APIキー・エラーログをAIのチャットに貼るな（外部サーバーに記録が残る）

### ログの管理

- アクセスログ・エラーログを必ず残す（保存先はアプリサーバーとは別に分離する）
- 定期的に目を通す習慣をつける（週一でも可）
- 異常検知アラートを設定する（自分で定期確認する前にシステムが知らせる状態に）
- **ログに機密情報を流さない**（パスワード・APIキー・クレカ番号・個人情報）

## 第二条：コストを事前に見積もり、定期的に確認せよ

「使った分だけ払う」モデルは**放置すると青天井**になる。

### 実装前にやること

- 課金単位（リクエスト数・トークン数・読み取り回数・ストレージ量）を公式ドキュメントで確認
- 「1日100人が10回使ったら月いくら？」を手を動かして試算する
- ハードリミットが設定できるサービスを選ぶ
- 無料枠の終了後・トライアルクレジット切れ後の挙動を読む

### リリース後にやること

1. **予算アラートを最初に設定する**（これをやる前にコードを書くな）
2. リリース直後は**毎日**請求ダッシュボードを確認する
3. **週次・月次**でトレンドを確認する（じわじわ増加は日次では気づきにくい）

---

## 第三条：法的適法性を最初に確認せよ

コードを書く前に考える：

- スクレイピング可否（利用規約）
- 個人情報の取り扱い（個人情報保護法・GDPR）
- ライブラリのライセンス（商用OK？ GPL汚染の可能性は？）
- AIが生成した画像・文章の著作権リスク
- 医療・金融・法律など業法規制のある領域への抵触

## 第四条：「使い捨てか？」を自問せよ

週末に自分だけが使って月曜に捨てるアプリなら不要。  
**誰かに使ってもらう・継続稼働するアプリ**ならここからが本番。

### データ設計の重要性

> コードのバグは直せる。データ構造の負債は、利息がついて返ってくる。

設計前に確認すべきこと：

- **エンティティの洗い出し**（「ユーザー」「注文」「商品」を自分の言葉で説明できるか）
- **関係性の整理**（1対多・多対多を把握しておかないと後からテーブルの作り直しが必要になる）
- **変わりやすい項目の特定**（将来増える可能性のある属性は別テーブルにすべきか）
- **削除方針の決定**（物理削除 vs 論理削除 ─ 後から変えると影響範囲が広い）
- **AIが作ったテーブル構造を必ず確認する**（AIは「動くもの」を出すが「変えやすい設計」を優先しない）

データ変更時の鉄則：
1. 本番DBに自動バックアップを設定する（最初にやる）
2. マイグレーションは**ステージング環境でテスト→本番適用**
3. 本番データをコンソールで直接操作しない（スクリプト経由で実行）

### トランザクションと冪等性

「途中で落ちたら何が起きるか」を常に考える：

- **トランザクション境界**：「全部成功するか全部なかったことにするか」の宣言
- **冪等性**：「同じ処理を何回実行しても結果が同じ」性質 → 二重課金・二重注文を防ぐ

> AIに処理を書かせたら「これ、途中で落ちたらどうなる？」「2回呼ばれたらどうなる？」と必ず確認せよ。

### AIに有意義なテストを書かせるには

「テストを書いて」と丸投げすると**ハッピーパスしか書かない**。ステップを分けて確認する：

1. 「今回実装した部分の仕様書を作って」→ 仕様の網羅性を確認
2. 「仕様から網羅的なテストケースを洗い出して、自動テスト範囲・人的確認範囲を整理して」→ ドキュメント確認
3. 「自動テストでカバーすべき範囲を実装して」→ 実装確認
4. 「結合してテストすべきケースを洗い出して」→ 結合テスト実施

AIが書いたテストで確認すること：
- テスト名が仕様になっているか（`test_1` ではなく「注文金額が0円のとき注文を拒否する」）
- Arrange / Act / Assert が明確か
- モックが多すぎないか（モックだらけのテストは「コードがモックを呼んだか」しか検証しない）
- 実装の詳細（プライベートメソッド・内部変数）に依存していないか

### 保守性・バージョン管理

- **DRY**: 同じロジックを2箇所以上に書かない
- **説明できないものはリリースするな**: 自分の言葉でコードの意味を説明できる状態を保つ
- **Git必須**: 小さく頻繁にコミット、`gitignore` でシークレットを除外、リポジトリは最初は必ずプライベート

### 開発環境の分離

本番で「ちょっと試す」が事故の99%の原因。必ず分離する：

| 環境 | 用途 |
|---|---|
| 開発（ローカル） | 自分のPCで試す |
| ステージング | 本番と同じ構成のテスト用 |
| 本番 | ユーザーが使う場所 |

最低でも開発と本番のDBを分けること。

## 第五条：性能を見積もれ

- ユーザー10人ならどんな実装でもよい
- 1万人になった瞬間、ループ内DBクエリ（**N+1問題**）がサーバーを溶かす
- データ100万件を超えると、インデックスなしの検索は数十秒かかる

最初から完璧にしなくてよい。**「今のコードは何件まで耐えられる設計か」をぼんやりと把握しておけ。**

---

## 第六条：先人の失敗から学び、失敗したら正しく対処せよ

### 失敗時の対処手順

1. **まず止める**: アプリを止め、APIキーを無効化し、被害を最小化する
2. **記録する**: 発生時刻・検知経緯・その時点でわかっていること
3. **早く知らせる**: 「調査中です」でいい。黙っていることが最も信頼を失う
4. **原因を突き止める**: 表面の症状ではなく「なぜそれが起きたか」を掘る（「個人のミス」で終わらせない）
5. **再発策を仕組みで作る**: テスト・アラートの見直しなど構造で防ぎ、失敗の原因を抽象化して記録に残す
