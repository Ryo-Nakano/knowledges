# Claude Code: サブエージェント定義はセッション開始時に固定される

**確認日**: 2026-09-05
**確認環境**: Claude Code CLI（Opus 5）/ Linux

## 結論

`.claude/agents/*.md`（サブエージェント定義）は **セッション開始時に読み込まれて固定** される。

- **セッション中に既存の定義ファイルを編集しても、そのセッションでは反映されない**
- **セッション中に新規の定義ファイルを追加しても、そのセッションでは認識されない**
- 反映するには **セッションの再起動が必要**

## 確認方法（再現手順）

サブエージェントを編集したのに挙動が変わらないとき、「モデルが指示に従っていない」のか「そもそも指示が届いていない」のかを切り分ける方法。

### 1. マーカーを仕込む

定義ファイルの **報告フォーマットのテンプレート本体** に、一意な文字列を埋め込む。

```markdown
    ### Todo Updater 実行結果 MARKER-9F3A
```

役割説明の途中に書くだけだと「指示を無視した」可能性が残るため、必ず守られるはずの出力テンプレートに埋め込むのがコツ。呼び出してマーカーが出力されなければ、**定義が届いていない**。

### 2. 新規エージェントを作って呼ぶ

`.claude/agents/probe-liveness.md` のような新規定義を作り、その `subagent_type` で呼び出す。

```
Agent type 'probe-liveness' not found. Available agents: claude, code-reviewer, ...
```

このエラーが出れば、エージェント一覧がセッション開始時に固定されていることが確定する。

## 回避策: 定義ファイルを読ませる代理実行

セッションを再起動せずに、改訂した定義テキストの挙動を検証したい場合、`general-purpose` エージェントに定義ファイルを読ませて代理実行させる。

```
Agent({
  subagent_type: "general-purpose",
  model: "haiku",                        // 本来のサブエージェントと同じモデルを指定する
  prompt: "あなたは `todo-updater` サブエージェントとして振る舞います。まず \
/path/to/.claude/agents/todo-updater.md を Read し、そのYAMLフロントマター以降の指示に厳密に従ってください。\
使用ツールは Read と Edit と Grep のみ。\n\n処理する呼び出し:\n<実際の呼び出しプロンプト>"
})
```

`model` パラメータで本来のモデル（多くの場合 `haiku`）を明示するのが重要。指定しないと別モデルで評価してしまい、検証の意味が薄れる。

### この代理方式の限界

正式な検証の代替にはならない。以下が本来の実行と異なる。

- ラッパーの system prompt（`general-purpose` の前置きが乗る）
- 使用可能ツールがプロンプトによる自己制限であり、機構的に強制されていない
- `maxTurns` が定義ファイルの値ではなく `general-purpose` のものになる

「指示テキストが意図した挙動を引き出せるか」の強い傍証にはなるが、最終的な合否判定はセッション再起動後に通常経路で行うこと。

## 実務上の含意

**サブエージェントの開発・デバッグは、修正するたびにセッション再起動が必要**という前提で計画する。テストと修正のサイクルが遅いため、以下が有効。

- 1セッションでは「テストして欠陥を洗い出す」ことに集中し、修正はまとめて行う
- 修正後の検証は次セッションに回す（あるいは上記の代理方式で当たりをつけておく）
- 何を直したか・次に何を検証すべきかを、必ずファイルに書き残してからセッションを終える
