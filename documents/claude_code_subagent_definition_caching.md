# Claude Code: サブエージェント定義の反映範囲

**確認日**: 2026-09-05
**確認環境**: Claude Code CLI（Opus 5）/ Linux

## 結論

`.claude/agents/*.md` の扱いは、**「エージェント名のレジストリ」と「定義の本文」で挙動が異なる**。

| 対象 | セッション中の変更が反映されるか |
|---|---|
| エージェント名の**レジストリ**（どの `subagent_type` が呼べるか） | **反映されない**。セッション開始時に固定される。新規の定義ファイルを追加しても `Agent type 'xxx' not found` になる |
| 登録済みエージェントの**定義本文・frontmatter**（役割・制約・処理フロー・`tools:` など） | **反映される**。呼び出しのたびにディスクから読み直される |

つまり、**既存のサブエージェントの改修はセッションを再起動せずに反復できる**。新しいサブエージェントを追加したときだけ再起動が必要。

## 「定義が届いていないのでは」と疑ったときの切り分け方

サブエージェントを直したのに挙動が変わらないとき、「モデルが指示を守っていない」のか「指示自体が届いていない」のかを切り分けたくなる。**このとき、指示の遵守を観測する方法を使ってはいけない。**

### やってはいけない検証: マーカーを仕込む

定義ファイルの報告フォーマットに一意な文字列（例 `MARKER-9F3A`）を埋め込み、出力されるかを見る方法。

**これは偽陰性を出す。** 実際にこの方法で「マーカーが出力されない → 定義がキャッシュされている」と誤った結論を出した。真相は、モデルがその指示を守らなかっただけだった。**指示不遵守が既知の問題であるモデルに対して、指示の遵守を観測する検証は証拠能力がない。**

### 正しい検証: モデルの意思が介在しない観測量を使う

**frontmatter の `tools:` に新しいツールを追加し、そのツールが使えるかを見る。**

```yaml
tools: Read, Edit, Grep   # ← Grep を追加してみる
```

呼び出して `Grep` が使えれば、frontmatter が読み直されている証拠になる。モデルは持っていないツールを使えないし、持っているツールの存在を隠す動機もないため、**モデルの気分に左右されない**。

新規ファイルが認識されるかは、新しい定義を作って呼び出し、`Agent type not found` が出るかで判定する（こちらはレジストリの検証であり、上記とは別の機構）。

## 教訓

**LLMの挙動を調べる実験では、「モデルが何を出力したか」ではなく「モデルの意思が介在しない観測量」を測ること。** 出力ベースの観測は、モデルが指示に従わなかっただけの場合と、そもそも指示が届いていない場合を区別できない。

あわせて、**1回の観測から重い結論を出さないこと。** 上記の誤った結論は n=1 の観測に基づいており、「全テストのやり直し」「次セッションへの持ち越し」という高コストな判断につながった。3回実行して再現性を確認する方法論を自分の判断にも適用すべきだった。
